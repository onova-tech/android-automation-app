## Risk Assessment Methodology

Each risk is assessed on:
- **Likelihood**: High (likely to occur), Medium (possible), Low (unlikely)
- **Impact**: High (project blocker), Medium (significant delay), Low (minor issue)
- **Severity**: High (critical), Medium (important), Low (acceptable)
- **Showstopper**: Whether the risk prevents project completion

## Critical Risks (Severity: HIGH)

### R1: FLAG_SECURE Blocks Accessibility Tree Inspection

| Field | Value |
|-------|-------|
| **Risk** | FLAG_SECURE blocks Accessibility Services from reading UI |
| **Likelihood** | High |
| **Impact** | High |
| **Severity** | Critical |
| **Showstopper** | YES (for some apps) |

**Description**: Apps setting `WindowManager.LayoutParams.FLAG_SECURE` prevent Accessibility Services from accessing their UI tree. The accessibility node returns null or empty.

**Affected Apps**: Banking apps, WhatsApp media previews, Netflix/Disney+ DRM, secure folders

**Evidence**: Android documentation explicitly states FLAG_SECURE prevents screen capture and accessibility inspection. This is intentional security design.

**Mitigation**:
- Document which apps are automation-compatible
- Build OCR fallback for visible content (Phase 2+)
- For POC, avoid testing on FLAG_SECURE apps

**Residual Risk**: Medium — Cannot automate banking/DRM apps. This is an acceptable limitation for Phase 1.

---

### R2: Resource IDs Change on App Updates

| Field | Value |
|-------|-------|
| **Risk** | Android resource IDs (R.id.*) change with every app update |
| **Likelihood** | High |
| **Impact** | Medium |
| **Severity** | High |
| **Showstopper** | NO (mitigable) |

**Description**: Android resource IDs are generated by the build system (AAPT/AAPT2). They are not guaranteed to be stable across app updates.

**Impact**: Workflows using `resource_id` selectors will break when the target app updates.

**Mitigation**:
- Support **multi-strategy selectors** with fallback chains
- Prioritize `text` and `content_description` selectors over `resource_id`
- Provide workflow validation tool to detect broken selectors
- Version workflows alongside app versions

**Residual Risk**: Medium — Requires workflow maintenance but doesn't block POC.

---

### R3: OEM Battery Optimization Kills Accessibility Service

| Field | Value |
|-------|-------|
| **Risk** | OEMs kill background services aggressively |
| **Likelihood** | High |
| **Impact** | High |
| **Severity** | High |
| **Showstopper** | NO (mitigable) |

**Description**: Samsung, Xiaomi, Huawei, Oppo, and other OEMs implement aggressive battery optimization that kills background services.

**Affected Behaviors**:
- Service killed after screen off
- Service killed when battery optimization threshold reached
- No notification of service being killed

**Mitigation**:
- Request `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` permission
- Show guided setup wizard to disable optimization
- Use foreground service (required since API 26)
- Document which OEMs need special handling

**Residual Risk**: Medium — Requires user configuration but is well-understood.

## High Risks (Severity: MEDIUM-HIGH)

### R4: Encrypted Keyboards Block Text Input

| Field | Value |
|-------|-------|
| **Risk** | `INPUT_METHOD_SECURE` prevents text injection |
| **Likelihood** | Medium |
| **Impact** | Medium |
| **Severity** | Medium |
| **Showstopper** | NO (known limitation) |

**Description**: Apps using secure keyboards (password managers, banking) prevent Accessibility Services from injecting text via `ACTION_SET_TEXT`.

**Mitigation**:
- Detect secure keyboard usage (check `InputMethodService` flags)
- Log warning and skip protected fields
- Consider ADB-based input for specific use cases

---

### R5: Custom Views Not in Accessibility Tree

| Field | Value |
|-------|-------|
| **Risk** | Custom-drawn views (Canvas, OpenGL) not in accessibility tree |
| **Likelihood** | High |
| **Impact** | Medium |
| **Severity** | High |
| **Showstopper** | NO (mitigable via OCR) |

**Description**: Views that draw directly via Canvas (games, charts, custom UI libraries) do not participate in the accessibility tree.

**Mitigation**:
- Build OCR fallback using Android's `ImageAnalysis` API
- Use screen coordinate tapping as last resort
- Document which apps support accessibility automation

---

### R6: Android Fragmentation (10K+ Devices)

| Field | Value |
|-------|-------|
| **Risk** | Different devices behave differently |
| **Likelihood** | High |
| **Impact** | Medium |
| **Severity** | Medium |
| **Showstopper** | NO (expected) |

**Description**: 10,000+ Android device configurations. OEM customizations, screen sizes, Android versions, and hardware differences create testing complexity.

**Mitigation**:
- Test on minimum 5 device profiles for POC
- Document supported OEMs and Android versions
- Use density-independent coordinates where possible
- Accept that some workflows will be device-specific

## Medium Risks (Severity: MEDIUM)

### R7: Play Store Policy Rejection

| Field | Value |
|-------|-------|
| **Risk** | Play Store may reject Accessibility Services app |
| **Likelihood** | Medium |
| **Impact** | High |
| **Severity** | Medium |
| **Showstopper** | NO (sideload for Phase 1) |

**Description**: Google scrutinizes apps using Accessibility Services for potential misuse (clickjacking, data scraping).

**Mitigation**:
- Target sideload distribution for Phase 1
- Prepare Play Store compliance documentation for Phase 2
- Emphasize local-first, no-data-collection design

---

### R8: User Trust and Permission Fatigue

| Field | Value |
|-------|-------|
| **Risk** | Users reluctant to grant Accessibility permissions |
| **Likelihood** | High |
| **Impact** | Medium |
| **Severity** | Medium |
| **Showstopper** | NO (education) |

**Description**: Accessibility Services permission is sensitive. Users may be wary of granting it to unknown apps.

**Mitigation**:
- Transparent UI showing what automation is doing
- Minimal permissions (only what's needed)
- Clear documentation of data access
- Open source for transparency

---

### R9: Deep Accessibility Trees Cause Performance Issues

| Field | Value |
|-------|-------|
| **Risk** | Complex layouts with deep trees cause slow traversal |
| **Likelihood** | Medium |
| **Impact** | Medium |
| **Severity** | Medium |
| **Showstopper** | NO (mitigable) |

**Description**: Some layouts (complex lists, nested RecyclerViews) have very deep accessibility trees. Traversal can be slow.

**Mitigation**:
- Configurable depth limits
- XPath-style optimized traversal
- Cache frequently-accessed tree sections
- Profile during POC
